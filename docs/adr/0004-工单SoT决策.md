# ADR-0004: 工单真值（SoT）归属 —— ITmanager 自持，GLPI 降级为可选只读参考

**状态**: ✅ 已采纳 (2026-09-09)
**日期**: 2026-09-09
**决策者**: 主人 (燕如) + 助手
**关联**: [ADR-0003](0003-grpc-作废与三层定位.md)、[v3 架构优化需求](../v3-架构优化需求.md)、[05-运维工单](../../05-运维工单.md)

---

## 背景

设计文档 `05-运维工单.md` 初版把 GLPI 写成工单系统选型（§5.1「工单系统选型：GLPI」），并给出 Zabbix → GLPI 建单的联动设计。但 2026-09-09 实测：

| 事实 | 证据 |
|---|---|
| **GLPI 没有部署** | `docker-compose.yml:116` 只有服务定义，环境里没有实例；`GLPI_URL` 为空即未启用（`integration_handler.go:107`） |
| **GLPI 客户端只能读** | `backend/internal/integration/glpi.go` 仅 `InitSession` / `GetTickets` / `KillSession`，无写方法 |
| **同步方向是 GLPI → 本地** | `SyncFromGLPI`（`integration_handler.go:71-73`）、`GLPITicket.ConvertToTicket()`（`glpi.go:156`） |
| **ITmanager 已有完整工单 CRUD** | `TicketService` = List/Get/Create/Update（`ticket_service.go:27-32`），路由 `routes.go:261-266` |

即：文档描述的是「以 GLPI 为中心的工单体系」，实际是「ITmanager 有一套能用的工单，GLPI 侧只有一个没部署的对端和只读拉取」。

## 选项

| 方案 | 内容 | 优点 | 代价 |
|---|---|---|---|
| **A. ITmanager 为 SoT** | `tickets` 表是唯一真值；GLPI 只做可选只读参考 | 无跨系统写冲突；不依赖未部署的系统；工单与告警/资产/时间线同库 | 工单能力自己维护（范围见 05 §5.3） |
| B. GLPI 为 SoT | ITmanager 只读 GLPI，写操作回 GLPI API | 复用成熟 ITIL 流程 | 功能挂在未部署的系统上；需双向同步 + 账号打通；与 ADR-0003 的「ITmanager = 人的操作台」冲突 |

## 决策

**采纳 A。**

1. **ITmanager `tickets` 表是工单唯一真值**：创建、查询、状态流转、指派、与告警/资产关联全在本系统内完成。
2. **GLPI 降级为「可选只读参考」**：配置项、连通性测试、`SyncFromGLPI` 只读拉取保留；`docker-compose.yml` 的 `glpi:` 服务定义保留但**默认不启用**。**不做 GLPI 写回**。
3. **明确不做**：ITIL 审批流（`ticket_approvals`）、SLA 引擎（`ticket_sla`）、满意度调查（`satisfaction`）、工单工作流引擎（`ticket_workflows`/`ticket_templates`）、子步骤（`ticket_steps`/`ticket_progress`/`step_progress_history`）、分段交接（`ticket_segments`/`ticket_handoffs`）。这些表在迁移里存在但 **0 行 Go 代码**，只归档不删除。
4. **AI 层不得写工单**：不向 HolmesGPT toolset 暴露建单/改单端点（与 ADR-0003 硬约束一致）。

**触发复评的条件**：组织统一部署 GLPI 并要求工单入口归口；出现跨部门 ITIL 刚性流程；工单量需要独立 SLA 引擎。届时**优先评估「GLPI 为 SoT + ITmanager 只读」**，而不是双写。

## 影响

- `05-运维工单.md` 重写：§5.1 改为 SoT 决策，§5.3 增「明确不做」清单，§5.5 补记三个缺陷。
- `08-部署运维.md`：GLPI 标注为可选 / 未部署。
- 工单相关的 KPI（MTTR）依赖 `resolved_at` / `closed_at`——**模型有、迁移没有**，须等 D-1 修复后才准（见 Risk-2）。

## Risk

| # | 失败模式 | 缓解 |
|---|----------|------|
| 1 | **双真相**：将来 GLPI 上线后有人同时往两边写，ITmanager 已 closed、GLPI 仍 open | 单一写入方；GLPI 侧只读拉取；若真要以 GLPI 为准，走本 ADR 复评，不做双写（与 ADR-0003 R4 告警划界同一原则） |
| 2 | **D-1 未修就上生产**：迁移与 GORM 模型列不一致（交集仅 10 列），生产走 `migrate.Up`（`main.go:34` → `database.go:72-73`），GORM 的 INSERT 引用迁移里不存在的列 → `POST /tickets` 必然失败。有人图省事用 `AutoMigrate`「修一下」，GORM 只加列不删约束，`ticket_no`/`creator_id` 的 `NOT NULL` 仍在，写入照样失败，且掩盖了漂移 | 修复另立任务：先定方向 → 写显式迁移 → 改模型与测试 schema；**禁止对生产库 AutoMigrate**；修复后加「用迁移建库跑一次 POST /tickets」的集成测试（现有测试 schema 与模型一致，CI 是盲的） |
| 3 | **历史 GLPI 工单重复导入**：`external_id` 无唯一约束，重复同步产生重复工单 | 导入走幂等 upsert；`external_id` 加部分唯一索引（仅 `source='glpi'` 且非空时生效） |
