# ADR-0005: 角色词表归一 + 能力矩阵鉴权

**状态**: ✅ 已采纳 (2026-09-09)
**日期**: 2026-09-09
**决策者**: 主人 (燕如) + 助手
**关联**: [ADR-0003](0003-grpc-作废与三层定位.md)、[FIX-PLAN-AUTHZ](../FIX-PLAN-AUTHZ.md)、[06-用户权限](../../06-用户权限.md)、[10-安全合规](../../10-安全合规.md)

---

## 背景

ITmanager 的路由门禁在 2026-09-09 实测出四个互相纠缠的问题（证据见 `docs/FIX-PLAN-AUTHZ.md` §1）：

| # | 问题 | 证据 |
|---|---|---|
| 1 | **五处角色词表互相漂移** | 迁移 `roles.code` = `admin/ops_admin/ops_user/readonly/auditor`；`cmd/seed` 写 `operator`；`models/user.go` 注释写 `admin/operator/readonly`；openapi + 前端写 `admin/operator/viewer`；迁移 000013 兜底值 `user`（不在 `roles` 表里） |
| 2 | **`RequireRole("admin")` 只认字面量** | 17 处调用覆盖 18 条路由；矩阵里的 `ops_admin` / `auditor` 走到这些路由一律 403 |
| 3 | **`auditor` 角色失效** | `auditor` 在 `roles` 表里存在，但没有任何端点区分它与 `readonly`，审计员读不了审计日志 |
| 4 | **破坏性路由无门禁** | 约 31 条非 GET 路由未挂门禁，任何已认证身份（含 `readonly`）可删资产/删告警/改集成凭据；`GET /api/notification-channels` 响应体含渠道明文凭据却人人可读 |

问题 1 与 2 互相锁死：想给 `ops_admin` 开门就得先有权威词表，而词表不统一时「改对」无法验证。

## 选项

| 方案 | 内容 | 优点 | 代价 |
|---|---|---|---|
| **A. 能力矩阵 + 单点词表** | 权威词表收敛到 `middleware/roles.go` 一处；鉴权按**能力档位**（read/write/manage/audit/identity）而非角色字面量 | 新增角色/端点只改一处；`RequireRole` 的「多词表」问题从根上消失；能力集可下发给前端 | 需要一次性迁移存量数据与 5 处词表；`read` 语义需要额外说明 |
| B. 只统一词表，保持端点级角色白名单 | 把 5 处词表改成同一份，`RequireRole` 改成 `RequireAnyRole("admin","ops_admin")` | 改动小 | 每加一个角色要改 N 处路由；端点 × 角色矩阵散落在 `routes.go`，无法测试穷举 |
| C. 引入 Casbin 等外部 RBAC 引擎 | 用策略文件描述权限 | 表达力强、生态成熟 | 新依赖 + 新配置面；当前规模（6 角色 × ~50 路由）用不上；违反「不引入没要求的抽象」 |

## 决策

**采纳 A。**

1. **权威词表**（`middleware.Role*` 常量，唯一来源）：

   | 角色 | 含义 |
   |------|------|
   | `admin` | 超级管理员，完全控制 |
   | `ops_admin` | 运维管理员：业务写 + 破坏性删除 + 集成/渠道配置 |
   | `ops_user` | 运维人员：业务写，无删除、无凭据配置 |
   | `auditor` | 审计员：只读 + 审计日志 |
   | `readonly` | 只读用户 |
   | `user` | 兜底最小权限（迁移 000013 引入，等同 `readonly`） |

2. **遗留别名只读入不写出**：`operator` → `ops_user`，`viewer` → `readonly`。保留是为了存量 dev 库与未过期 JWT（24h）不静默降权；**v4 清理**。

3. **能力矩阵**（`middleware.Capability`，实现在 `capRoles`）：

   | 能力 | admin | ops_admin | ops_user | auditor | readonly/user/未知 |
   |------|:-----:|:---------:|:--------:|:-------:|:-----------------:|
   | `read` | ✅ | ✅ | ✅ | ✅ | ✅ |
   | `write` | ✅ | ✅ | ✅ | ❌ | ❌ |
   | `manage` | ✅ | ✅ | ❌ | ❌ | ❌ |
   | `audit` | ✅ | ✅ | ❌ | ✅ | ❌ |
   | `identity` | ✅ | ❌ | ❌ | ❌ | ❌ |

4. **`read` 是地板，不是「所有 GET」**：语义为「**未被更高能力覆盖的端点**默认放行」。因此 `GET /api/users`（`identity`）、`GET /api/audit-logs`（`audit`）、`GET /api/notification-channels`（`manage`）、`GET /api/diagnostics/{ping,traceroute}`（`write`，服务端外连）都是显式例外。完整清单见 `docs/FIX-PLAN-AUTHZ.md` §3.3。

5. **`manage` 与 `write` 的分界 = 不可逆或涉及凭据**。资产软退役（`retire`）可逆 → `write`；硬删 → `manage`。

6. **fail-safe**：空/未知角色只放行 `read`；**未登记的能力一律拒绝**（新增能力必须显式写进 `capRoles`）。

7. **单点判定**：路由一律用 `middleware.RequireCapability(cap)`，**禁止**在 handler/路由里比较角色字面量。`RequireRole` 保留仅供测试，新代码不得使用。

8. **双向兜底**：`internal/api/routes_integration_test.go` 用 `r.Routes()` 枚举全部注册路由，**非 GET 路由必须显式分类**（挂能力或进 `nonGetUngated` 白名单），否则测试失败 —— 兜住「新增路由忘挂门禁」。

9. **`/auth/me` 下发 `capabilities`**（数据源 = JWT claims 里的 role，与鉴权同源），前端不再自己复制一份矩阵。

10. **矩阵可达性**：新增 `cmd/set-role`（env 驱动，直连 DB）让 `ops_admin` / `ops_user` / `auditor` 在生产有分配路径；含**防自锁**（拒绝降级最后一个 `admin`）。

## 后果

**正面**：

- 新增端点只需在 `routes.go` 挂一个能力；新增角色只改 `capRoles` 一处（改错会被矩阵测试与路由清单测试挡住）。
- `auditor` 角色从「有名无实」变成可用；`admin` 与 `ops_admin` 因 `identity` 有实际分界。
- `readonly` 不再能删资产 / 改集成凭据 / 读渠道明文凭据。

**代价与已知缺口**：

- **存量 `user` 角色静默降权**：迁移 000013 的兜底 `user` 在旧行为下能写，现在只能读。缓解：这是 fail-safe 的**预期方向**，且 `cmd/set-role` 可一键提权。
- **JWT 内嵌 role 且不回查 DB** → 角色变更最长 **24h** 后才在旧令牌上生效。缓解：`cmd/set-role` 文档中注明；紧急场景需用户重新登录。
- **API Key 的 scope 只按 HTTP 方法判定**（GET → read，其余 → write，`auth.go:196`），无法表达「GET 但属 `manage`」。因此 API Key 访问 `GET /api/notification-channels` 会被 `manage` 能力挡住 —— 这是**收紧**方向，可接受；细粒度 scope 属独立任务。
- **`/auth/me` 的 `capabilities` 暂无消费者**：前端既未调用 `/auth/me`，也未读该字段（grep 零命中）。它是已批准需求的交付项（决策 9），但 UI 改造本轮不做；且 `/auth/me` 不在 `openapi.yaml` 里，`gen:api` 生成不到该字段的类型，**前端接入前需先补 spec**。
- **`GET /api/integrations/status` 仍回传集成 URL 与 Zabbix 用户名**（不含 token），属读地板。内网拓扑信息，若需收紧另立任务。
- **`cmd/set-role` 的并发窗口**：防自锁检查与写入已放进同一事务，但两个并发进程仍可能各自通过检查（TOCTOU）。缓解：该命令是人工运维操作，不在自动化路径上。
- **`POST /api/auth/skip-password-change` 可被空 body 绕过**：服务端只拒绝 `reason == "first_login"`，空 body 时 `req.Reason` 为空即清除强改密标记，seed 创建的 `admin/admin123` 可保留弱口令。**既有缺陷**，本轮明确不加能力（自助端点），单列任务。
- **write scope 的 API Key 挂在 admin 账号上可签发新 Key**：`apiKeyAllows` 只按方法判定，`identity` 路由的能力来自关联用户的角色。**既有缺陷**，单列任务。
- **前端 6 页 token 失效**（**已修复 2026-09-09**，见 `docs/FIX-PLAN-FRONTEND-TOKEN.md`）：`AlertSuppressions`/`Oncall`/`Runbook`/`Topology`/`MetricSnapshot`/`AssetTimeline` 曾用 `localStorage.getItem('token') ?? ''` 拼 Bearer，而该键自 C-F5 改 httpOnly cookie 后无人写入（恒 401 + 静默回退 mock）。已收敛为共享 `apiGet`/`apiSend` + 修 `/api/v1` 前缀 + ESLint 守卫。

## 复评条件

- 引入 LDAP/AD 组映射（`IT-Admin` 等）时，需要重新定义「外部组 → 本地角色」的映射表，矩阵本身不变。
- 出现「同一角色在不同租户/项目下权限不同」的需求时，能力矩阵退化为基线，需要引入 scope 维度（届时优先评估 Casbin，而不是继续加能力档位）。
- v4 清理遗留别名时，需确认存量库与在线 JWT 均已过期。
