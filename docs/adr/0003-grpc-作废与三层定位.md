## 决策一：作废 ADR-0002 的 gRPC 部分

### 背景

ADR-0002（2026-06-17）把 gRPC 内部通信列为 v2.0 决策，动机写的是：

> **动机**: 内部 handler → service → db 全 HTTP 链路, 加 s2s 通信 1 次 RTT 多 50ms, batch 操作 (BulkResolve) 慢。

### 问题

这个动机基于一个**错误前提**。本项目是**单体 Go 应用**：

```
handler ──函数调用──► service ──函数调用──► GORM ──► PostgreSQL
         （进程内，无网络）      （进程内，无网络）
```

`handler → service` 是**进程内函数调用**，本来就不存在 RTT。引入 gRPC 不会消除任何网络往返，反而新增：

| 代价 | 说明 |
|---|---|
| 序列化开销 | 每次调用多一次 protobuf marshal/unmarshal |
| 协议复杂度 | proto 文件 + 代码生成 + 双协议并存（REST + gRPC） |
| 调试成本 | 中间层不再是可断点的函数调用 |
| 部署复杂度 | 单机上的 localhost 监听 + 连接管理 |

### 实际情况（2026-09-09 复核 —— 本文档初版此处写错了）

v2.0.1 **已经交付了 gRPC 的一部分**：

| 交付物 | 位置 | 状态 |
|---|---|---|
| gRPC server（AlertService，端口 `:50051`，`GRPC_PORT` 可覆盖） | `backend/cmd/server/grpc.go` | ✅ 已实现，`main.go:74` 启动 |
| proto + 生成代码 | `api/proto/alert/v1/alert.proto`、`backend/api/proto/alert/v1/*.pb.go` | ✅ |
| 服务实现 + 10 个单测 | `backend/internal/grpcserver/alert_server.go`(`_test.go`) | ✅ |
| **gRPC 客户端（仓库内调用方）** | 全仓库无 | ❌ 只有生成的 `NewAlertServiceClient` 存根 |

即：**ADR-0002 设想的「handler→service 全走 gRPC + REST 走 gRPC-gateway + alert/ticket/asset 三域」并未落地**；落地的是「额外挂一个 AlertService 的 gRPC 端点」。REST 链路与 handler→service 的调用方式**都没变**。

> 更正记录：初版写「CHANGELOG 显示 v2.0.1 已将其推迟」，与 CHANGELOG 实际内容相反（v2.0.1 条目是「🔌 **gRPC 内部通信** — AlertService s2s + proto contract」）。误判根因见下方附录。

### 决策

**1) 不再扩大 gRPC 范围**（v3 明确不做）：不补 ticket/asset 域、不做 gRPC-gateway、不改 handler→service 调用方式。ADR-0002 的其余决策（cursor 分页、event bus、in-process LRU 缓存、单机部署）**继续有效**。

**2) 已落地的 AlertService gRPC（`:50051`）—— 保留但冻结（主人 2026-09-09 拍板）**：

| 选项 | 理由 | 风险 |
|---|---|---|
| **A. 保留但冻结 ✅ 已采纳** | 已实现 + 有 10 个单测；为将来 s2s 扩展留余地 | 仓库内无调用方，长期是「无人使用的公开端口」 |
| B. 移除 ❌ 未采纳 | 全仓库无客户端；少一个暴露端口 | 若有外部调用方，属破坏性变更 |

「冻结」= 不扩展、不新增域、不改 handler→service 调用方式；代码与测试原样保留。

### 触发复评的条件（若未来出现）

- 服务被拆成**多进程/多机**（那才是真 RTT）
- 出现跨语言调用需求（Go 之外的调用方）
- 单进程吞吐成为瓶颈且已验证序列化不是瓶颈

> 在此之前，保持进程内函数调用。

### 附：这次误判的根因（已修复）

`.gitignore:10` 的 `server` 是**无斜杠宽匹配**——除了忽略构建产物，还忽略了源码目录 **`backend/cmd/server/`**（应用的 `main.go` 与 `grpc.go` 都在里面）。构建产物实际是 `backend/bin/server`，已被 `bin/` 覆盖，所以这条规则纯属误伤。

后果：`rg` / IDE 搜索 / 本机 `grep` 包装（ugrep `--ignore-files`）/ **codegraph 索引** 全部**静默跳过**该目录。查 gRPC 时看不到 `grpc.NewServer`，于是误判为「未实现」。只有 `command grep -r` 或 `rg --no-ignore` 能看到。

**处置**：`.gitignore` 第 10 行 `server` → `/server`（只锚定仓库根），源码目录恢复可见。
**教训**：忽略规则里的无斜杠名字会匹配任意层级同名目录；代码检索工具的「零命中」不等于「不存在」，先确认 ignore 规则。

## 决策二：v3 三层定位

### 背景

ITmanager 从「聚合层」逐步膨胀为「全栈自建平台」：设计文档 13 章、`schema.sql` 55 张表，其中 **40 张零代码实现**；同时与 NetBox / GLPI / HolmesGPT 存在重复建设（详见 [v3 架构优化需求](../v3-架构优化需求.md) §1）。

### 决策

**ITmanager 收敛为「人的操作台」，做三层分工：**

| 层 | 拥有什么 | 不做什么 |
|---|---|---|
| ① ITmanager | 人的**工作流**：拓扑 / 时间线 / 告警确认 / Runbook / 复盘 / 值班 / KPI | 不存资产真值、不做 AI 推理、不自建采集器 |
| ② NetBox | 资产**真值**（SoT）：设备 / 机柜 / IP / **专线 Circuits** / VM | 不做工作流、不做告警 |
| ③ Keep + HolmesGPT | 告警**收敛**与**根因** | 不做资产台账、不自动执行写操作 |

**硬约束：AI 层对本项目一律只读**；写操作（确认告警、建单）必须由人在 ITmanager 里点。

### 影响

- R1：`09-AI辅助.md` 自建 LLM 设计废弃，改为对接 HolmesGPT（只读 toolset）
- R2：自建 `lines` 系列四表废弃，专线归 NetBox Circuits
- R3：vCenter 走 NetBox sync，ITmanager 不直连
- R4：告警去重/关联归 Keep，ITmanager 保留人工抑制 + 值班升级
- R5：文档与 schema 与代码实际状态对齐
