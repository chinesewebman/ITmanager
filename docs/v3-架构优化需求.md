## 0. 一句话

**ITmanager 不再做「全栈自建平台」，收敛为「人的操作台」**：资产真值归 NetBox、AI 分析归 HolmesGPT、告警枢纽归 Keep，ITmanager 专注做运维人员每天真正会打开的那块屏幕。

## 1. 背景：基线盘点（2026-09-09 实测，非推测）

| # | 问题 | 实测证据 |
|---|---|---|
| P-1 | **定位漂移** | 设计文档 13 章 + 55 张表覆盖了 NetBox/Zabbix/GLPI/Graylog 已有的能力；`schema.sql` 55 张表中 **40 张零代码引用** |
| P-2 | **AI 模块是空壳** | `09-AI辅助.md` 纯设计；无 LLM 代码、无 `/api/v1/ai/*` 端点、无前端页面；`ai_conversations`/`ai_messages`/`llm_providers`/`kb_documents` 四表零引用 |
| P-3 | **专线设计得好但没做** | `lines`/`line_types`/`line_changes`/`line_monitors` 四表字段比 NetBox Circuits 更贴运维场景（含运营商故障电话、业务归属），但 **0 行 Go 代码**，且游离在资产图之外 |
| P-4 | **vCenter 零纳管** | `vmware_vms`/`vmware_hosts`/`vmware_connections`/`vmware_sync_history` 四表零引用；上千台 VM 无直接入账路径 |
| P-5 | **文档与代码脱节** | README/TODO/CHANGELOG 版本号三处过期；`schema.sql` 不含后期迁移新增表（`alert_suppressions`/`oncall_*`/`runbooks`/`metric_snapshots`） |
| P-6 | **ADR-0002 前提有误 + 文档误判** | 动机写「s2s 通信多 50ms RTT」，但 handler→service 是**进程内函数调用**，本无 RTT；且 v2.0.1 **实际已交付** AlertService gRPC（`:50051`，`backend/cmd/server/grpc.go`，`main.go:74` 启动），初版文档误写「已推迟」（根因见 ADR-0003 附录） |
| P-7 | **`.gitignore` 误伤源码** | 第 10 行 `server` 无斜杠宽匹配，忽略了源码目录 `backend/cmd/server/`（应用入口）；`rg` / IDE / codegraph 索引**静默跳过**该目录 |
| P-8 | **工单 SoT 悬空** | `05-运维工单.md` 把 GLPI 写成选型，但 GLPI **未部署**且客户端**只读**（`integration/glpi.go` 无写方法）；同时 `tickets` 存在**三套不一致 schema**（迁移 24 列 / 模型 24 列，交集仅 10 列 / 测试 schema 与模型一致 → CI 盲） |

**核心判断**：P-1 是病根。范围失控导致 40 张表只设计不实现，同时和 NetBox/GLPI 重复建设。

## 2. v3 目标定位：三层分工

```
┌──────────────────────────────────────────────────────────┐
│  ① 人的操作台 —— ITmanager（本项目）                      │
│  拓扑图 · 诊断时间线 · 告警确认 · Runbook · 复盘 PDF      │
│  值班排班 · KPI 报表 · 全局搜索                           │
└────────────────────────▲─────────────────────────────────┘
                         │ 只读消费
        ┌────────────────┴────────────────┐
        │                                 │
┌───────┴──────────────┐      ┌───────────┴──────────────┐
│ ② 资产真值 —— NetBox │      │ ③ AI 分析层               │
│ DCIM/IPAM/Circuits   │      │ Keep（告警枢纽）          │
│ 专线/设备/机柜/VM    │      │ HolmesGPT（根因侦探）     │
└──────────────────────┘      └──────────────────────────┘
```

**分工原则**：

| 层 | 拥有什么 | 不做什么 |
|---|---|---|
| ① ITmanager | 人的**工作流**：看、确认、排班、复盘 | 不存资产真值、不做 AI 推理 |
| ② NetBox | 资产**真值**：设备/机柜/IP/专线/VM | 不做工作流、不做告警 |
| ③ Keep + HolmesGPT | 告警**收敛**与**根因** | 不做资产台账、不自动执行写操作 |

**统一约束：AI 层对本项目一律只读。写操作（确认告警、建单）必须由人在 ITmanager 里点。**

## 3. 五个改造点

### R1 — AI 模块重定位：砍自建，改接 HolmesGPT

- **What**：`09-AI辅助.md` 从「自建 LLM 问答」改为「ITmanager 作为 HolmesGPT 的数据源」；删掉 `ai_conversations`/`ai_messages`/`llm_providers` 三表的设计（`kb_documents` 一并归档）。
- **Why**：自建是 prompt 一次性问答，HolmesGPT 是 agentic 多轮工具调用 + 证据链，能力代差明显（P-2）。
- **Where**：`09-AI辅助.md`、`schema.sql`、`docs/schema-planned.sql`。
- **How**：定义 3 个 HolmesGPT toolset 端点（见 §4 R1 验收）。
- **Risk**：**HolmesGPT 拿不到 ITmanager 独有的业务上下文**（诊断时间线、MTTR、Runbook 推荐），退化成只能查 Zabbix/Splunk 的通用侦探 → **缓解**：toolset 必须显式包含 `GET /api/v1/diagnostics/assets/{id}/timeline` 与 `GET /api/v1/runbooks/recommend`，不接受「给裸 API 让它自己猜」。

### R2 — 专线归属 NetBox Circuits

- **What**：废弃自建 `lines` 系列四表；专线以 NetBox `Circuit` + `CircuitTermination` 建模，ITmanager 只读渲染。
- **Why**：专线必须和设备/机柜/站点在**同一张资产图**里才有诊断价值（P-3）；NetBox 不支持虚拟电路建模，MPLS 按「每腿一条 Circuit 终止在 Provider Network」建模。
- **Where**：`02-资产管理.md`、`schema.sql`。
- **How**：NetBox 存 `circuit_id` + A/Z 端点 + 带宽 + 关键性；合同期/月租/运营商故障电话等 NetBox 缺失字段，由 ITmanager 以只读视图承载（或 NetBox Custom Field）。
- **Risk**：**NetBox Custom Field 承载不了复杂合同语义**（合同期、月租、变更审计）→ **缓解**：字段级切分写进 `02-资产管理.md`——NetBox 管「物理真值」，ITmanager 管「商务元数据」，以 `circuit_id` 关联，不做双写。
- **落地（2026-09-12）**：[`docs/adr/0006-r2-专线-circuit切分.md`](adr/0006-r2-专线-circuit切分.md)（决策记录）+ [`02-资产管理.md` §2.7](../02-资产管理.md)（字段级切分表）+ [`docs/FIX-PLAN-R2-NETBOX-CIRCUITS.md`](FIX-PLAN-R2-NETBOX-CIRCUITS.md)（修复方案）。字段级切分覆盖 `docs/schema-planned.sql:39-125` 全部 `lines*` 字段：A 组（物理真值 → NetBox 14 列）、B 组（商务元数据 → ITmanager `line_meta` 8 列）、C 组（审计 → ITmanager `audit_logs` / 监控 → Zabbix / 类型 → NetBox CircuitType）。

### R3 — vCenter 纳管：走 NetBox sync，不直连

- **What**：vCenter → NetBox 同步（`bb-Ricardo/netbox-sync`，社区版），ITmanager 从 NetBox 读 VM。
- **Why**：P-4，上千台 VM 零纳管；且 NetBox 是 SoT，VM 必须进同一张图。
- **Where**：`02-资产管理.md`、`03-监控采集.md`。
- **How**：NetBox 打 `NetBox-synced` 标签做孤儿识别。
- **Risk**：**VM 频繁增删产生大量孤儿对象**（快照/克隆/临时机）→ **缓解**：先 dry-run 跑一周，确认删除策略再开自动清理；删除前必须有人工确认窗口。

### R4 — 告警与 Keep 划界

- **What**：跨源去重/关联归 Keep；ITmanager 保留**人工抑制规则**（维护窗口）+ 值班升级。
- **Why**：功能重叠（P-1），两套并存会出现「双真相」。
- **Where**：`04-告警通知.md`。
- **How**：**Keep 是告警状态的唯一写入方**；ITmanager 只读展示 + 人工抑制。
- **Risk**：**两套状态不一致**（ITmanager 已 ack、Keep 仍 open）→ **缓解**：同上，单一写入方；ITmanager 的 ack 动作改为调用 Keep API，不落本地状态。
- **说明**：v3 **不部署** Keep（告警量未证实需要），只**划定边界**；先做 R1 直连 HolmesGPT。

### R5 — 文档与仓库卫生

- **What**：版本号对齐 `git describe`；`schema.sql` 拆分；ADR-0002 的 gRPC 部分作废；`.gitignore` 误伤修复。
- **Why**：P-5、P-6、P-7；过期文档比没有文档更糟（会误导后续开发）。
- **Where**：`README.md`、`TODO.md`、`CHANGELOG.md`、`schema.sql`、`.gitignore`、`docs/schema-planned.sql`（新）、`docs/adr/0003-*`（新）。
- **How**：见 §5 验收。
- **执行发现（2026-09-09）**：拆分时发现 **live 表 `assets` / `racks` 通过外键引用 `idc`**，若把 `idc` 一并移出会破坏 FK。处置：`idc` 保留在 `schema.sql`（标注「无 CRUD，仅因 FK 依赖保留」），实际移动 39 张表。
- **执行发现（2026-09-09，第二轮）**：`.gitignore:10` 的 `server` 宽匹配忽略了 `backend/cmd/server/`，导致 `rg` / IDE / codegraph 索引全部静默跳过应用入口 —— 这是 P-6 误判的直接原因。处置：改为 `/server`（构建产物实际在 `backend/bin/server`，已被 `bin/` 覆盖，此规则本就冗余）。
- **Risk**：**归档后有人误用旧 `schema.sql` 建库** → **缓解**：`schema.sql` 顶部加醒目 header，并写明「建库唯一途径是 `migrations/`」；`schema-planned.sql` 文件名即含 planned。

### R6 — 工单 SoT 归位：ITmanager 自持，GLPI 降级为可选只读参考

- **What**：`05-运维工单.md` 从「以 GLPI 为工单系统」改为「ITmanager `tickets` 表是唯一真值」；GLPI 只做可选只读参考；明确不做 ITIL 审批 / SLA 引擎 / 满意度 / 工作流引擎 / 子步骤。
- **Why**：P-8。GLPI 未部署且客户端只读，等于把工单功能挂在空中；ITmanager 已有可用 CRUD（`ticket_service.go:27-32`，`routes.go:261-266`）。
- **Where**：`05-运维工单.md`、`docs/adr/0004-工单SoT决策.md`（新）、`08-部署运维.md`。
- **How**：决策 + 边界 + 缺陷清单见 ADR-0004；GLPI 侧保留配置/连通性测试/只读拉取，不做写回。
- **Risk**：**将来 GLPI 上线后出现「双真相」**（ITmanager 已 closed、GLPI 仍 open）→ **缓解**：单一写入方；要以 GLPI 为准就走 ADR 复评，不做双写。
- **附带发现（阻断级，另立修复任务）**：见 §9 缺陷清单 D-1/D-2/D-3。

## 5. 明确不做（NOT doing）

| 不做 | 理由 |
|---|---|
| 自建 LLM 问答 / 知识库 | HolmesGPT 已覆盖且更强（R1） |
| 自建专线 CRUD | 与 NetBox Circuits 重复（R2） |
| gRPC 内部通信 | 进程内调用无 RTT，纯增复杂度（P-6） |
| 迁移到 Nautobot | 数据模型已分叉，迁移是真实工程；本项目不需要内置 Jobs |
| v3 部署 Keep | 告警量未证实需要；先 R1 直连 HolmesGPT |
| 删除历史表结构 | 只归档不删除，保留可追溯性 |
| GLPI 写回（建单 / 改单） | GLPI 未部署且客户端只读；工单 SoT 在 ITmanager（R6） |
| ITIL 审批流 / SLA 引擎 / 满意度 | 对应表 0 行 Go 代码；单团队运维不需要（R6） |
| 自动建单（AI 触发） | AI 层只读，写操作必须由人点（ADR-0003 硬约束） |

## 7. 多角度自审

| 角度 | 问题 | 结论 |
|---|---|---|
| **正确性** | 三层定位与 BCD 文档冲突吗？ | 不冲突：B 章=AI 层、D 章=NetBox SoT，本文档是 ITmanager 侧的落地映射 |
| **边界** | 专线「物理真值 vs 商务元数据」切分够清晰吗？ | 够，但**必须在 R2 落到字段级**（NetBox 存什么、ITmanager 存什么、以什么关联），否则执行时会双写 |
| **安全** | HolmesGPT 访问 ITmanager API 的权限边界？ | **必须只读 token + 最小 scope**；不得复用 admin 账号；写操作端点（ack/建单）不暴露给 toolset |
| **一致性** | 术语是否统一？ | 统一使用：**SoT**（NetBox）、**操作台**（ITmanager）、**AI 分析层**（Keep+HolmesGPT） |
| **可逆性** | 死表「清理」是否可逆？ | 是——只移动不删除，`docs/schema-planned.sql` 保留全部定义 |

**自审发现的待补项**：
1. R2 的字段级切分表本文档尚未给出 → 落到 `02-资产管理.md` 时必须补齐。
2. R1 的 toolset 端点清单是「最小集」，需要 HolmesGPT 侧实测确认可用性。
